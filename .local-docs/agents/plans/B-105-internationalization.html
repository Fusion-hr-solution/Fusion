Fusion in English, French and Arabic

Fusion will speak three languages, and Arabic reads right to left. Every screen we build now in hard-coded English with left/right spacing adds to the bill. This page sets out how I'd lay the foundation, and the few calls that are yours.

What to decide

Seven calls, all settled on 24 Oct 2026: the language lives on the account, the rest as recommended. Phase 1 is the OpenSpec change add-i18n-foundation.

I-1

Which library

My call

The shared @repo/i18n on next-intl 4, which Learning already runs.

It is built for the Next.js App Router and server components, formats dates, numbers and plurals with the browser's own locale data, and already sits in the repo. One library across every module means one cookie, one switch, and one way to write a translated sentence.

Also considered
  • i18next with react-i18next: mature, but its server-component story is bolted on, and it would be a second library next to Learning's.
  • Lingui or FormatJS: good extraction tooling, same objection: a second system.
I-2

How sentences are written in code

My call

Named keys in one catalogue per module (t("plan.write")), type-checked, with a check that every language has every key.

A typo in a key fails the type-check, and a missing French or Arabic line fails the check before it ships. That is how Learning works, so the gate already exists to copy. Each catalogue sits with its module; @repo/ds ships its own for shared parts such as the save bar.

Also considered
  • next-intl's useExtracted: you write the English inline and it generates keys and catalogues. Less friction for 2,800 strings, but it is marked experimental in 4.14. Worth a second look when the migration starts.
I-3

Where a person's language lives

Decided: on the account

On the person, in Identity, not only in the browser. Fusion uses the person's choice, then the company's default language, then English.

Emails and notifications are written on the server, after the person has closed the tab, so the server must know their language. It also follows them to their phone. The company default already exists as the tenant's locale, and it is where B-110's "make Fusion yours" meets this work.

The alternative
  • Keep it per device, as today: no backend work, but every email goes out in the company language whatever the person picked.
I-4

Right to left

My call

Set the page direction from the language, and build every layout with start/end instead of left/right, enforced by a lint rule.

The demo above shows the difference. With start/end, Arabic lays itself out: spacing, alignment, progress bars and drawers flip, and the shadcn direction provider in @repo/ds handles menus and the sidebar. Arrows that mean "forward" flip too; charts, numbers and code stay left to right. The rule is the same kind of guard as the radius and surface roles.

What it costs
  • Converting about 880 classes, mostly mechanical: pl- to ps-, text-left to text-start, left- to start-.
  • A look at each drawer, sheet and animated panel that slides in from a side.
I-5

Arabic type

My call

Pair Geist with an Arabic face of similar weight, such as IBM Plex Sans Arabic or Noto Sans Arabic, loaded only for Arabic letters.

Without it the browser substitutes whatever it has, and Arabic screens look unfinished. Loading the face only for Arabic letters keeps English and French pages as they are. This page uses Plex Arabic, so you can judge it in the demo.

I-6

Dates, numbers and plurals

My call

The date grammar in @repo/ds/lib/dates takes the language instead of a fixed en-GB; plurals go through the message format, never through count === 1.

Arabic has six plural forms: none, one, two, a few, many, and other. The slider in the demo walks through all of them. Tunisian Arabic formatting keeps Western digits, so figures read the same in all three languages.

I-7

Text the server writes

My call

Errors and in-app notifications travel as a code with values, and the screen turns them into a sentence. Emails are written on the server in the recipient's language. Change history stores what happened, not a sentence.

Performance already returns error codes, so screens can translate them without the backend learning three languages. Emails are the one place the server must write the words itself.

Order of work

Stop the bill growing

The lint rule for start/end with the 880 classes converted, one language cookie for every app, and the date grammar taking a language. Small, and every slice after it is cheaper.

The frame in English and French

Shell, @repo/ds, sign-in and Settings on the shared catalogues, with the parity check. The switch starts working for real.

Core HR, Performance and Platform

One module at a time, behind the same check, French reviewed by someone who writes it natively.

Arabic

Arabic catalogues, the Arabic face, and a right-to-left pass through every screen, dark at 1440×900 as usual.

The server in three languages

The person's language in Identity, emails per recipient, notification and error codes rendered on screen.

Decided

  1. I-3: a person's language lives on their account, so it follows them across devices and emails can use it.
  2. Learning: other contributors' modules only must not break. Phase 1 keeps the shared package at English and French, so Learning runs unchanged.
  3. Who translates: we draft French and Arabic ourselves; no native review step.
  4. When: phase 1 is proposed as add-i18n-foundation, applied once B-089 and B-071 are committed and B-071 is signed off.
