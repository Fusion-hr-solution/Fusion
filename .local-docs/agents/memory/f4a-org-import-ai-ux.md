**Interaction model (the durable design):** the workspace derives one **assistance phase** `interpreting → ready → applied` (+ `failed`), not raw issue counts. Helpers `isInterpretationIssue` / `interpretationNodeIds` in `import-review-model.ts` mark the AI-eligible issue kinds (`type`, `sourceMapping`). While interpreting/ready these are **excluded** from the "Needs attention" tally + footer blocker count + outline red status, so a term being interpreted never reads as a user failure. The AI moment rides Fusion's **amber `--primary`** (never purple/blue) with a restrained pulsing `Sparkles` (reduced-motion aware). Inspector = semantic translation: title "Fusion's interpretation / AI-assisted" (provenance once, no provider/model leak), a quiet "Structure detected" group for shape/field kinds, and a single `Your term → Fusion meaning` header over `sourceLabel → [select]` rows; only a **changed** row shows an "Edited" marker (the control is the only truth). Headline count = business-term interpretations (`organization_type_mapping`) only; structure rides along silently. Apply → toast "Interpretations applied", AI recedes, deterministic hierarchy dominates.

**Fresh-tenant "keeps asking me to Choose a type" fix (2026-08-21):** symptom — on a freshly provisioned tenant the interpretation never auto-fills the org-type meanings; user always lands on "Fusion found N meanings to confirm · Needs a type". Root cause (proven via DB + live Groq repro, NOT config): the import fires **two sequential Groq calls** — field-mapping (succeeds, supersedes) then organization_type_mapping (the heavier one). The type call was failing (`Failed/ProviderUnavailable`, `SuggestionsJson []`) so both terms fell through to the manual queue; the frontend auto-generate fires **once per fingerprint (`generatedRequestRef`) and never retries**, so one transient failure = permanent manual. Why fragile: model `openai/gpt-oss-120b` is a **reasoning model** (~400–1000 hidden reasoning tokens/call) and the Groq free/on_demand tier is **8000 TPM, shared identically across every model on the account** (gpt-oss-120b/20b/qwen all report `x-ratelimit-limit-tokens: 8000` — switching model does NOT raise it; llama-3.x return 404, no access). Two reasoning calls per import + repeated imports blow the minute budget → the 2nd call throttles/errors. Worked tenants (tenant10/Atlas) only "work" because they had cached Available/Applied attempts. **Fix (2 CoreHR files, no frontend change):** (1) `GroqOrganizationImportSemanticProvider` request now sends `reasoning_effort: "low"` + `max_completion_tokens` 1200→800 — cut reasoning tokens 402→128, completion 483→309, `finish=stop`, still coherent distinct mappings, and shrinks the per-call TPM reservation so both calls fit. (2) `OrganizationImportSemanticAssistanceService.SuggestWithRetryAsync` — bounded retry (new option `MaxProviderAttempts`, default 3, clamp 1–5, validated) with exponential backoff 0.75/1.5/3s floored by provider Retry-After, capped 10s, over transient categories only (RateLimited/ProviderUnavailable/Timeout); NotConfigured/InvalidOutput still fail fast; caller-cancel → Interrupted. Compiles clean (csc ok; only bin-copy blocked while the dev CoreHR PID is running). **Requires CoreHR restart to take effect; full build+tests couldn't run while the service held the dll.** See [[local-dev-auth]] for the demo login.
