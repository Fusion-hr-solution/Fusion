Second section of `/performance/team` ("Your People") — the manager's operational roster for the current cycle. Built 2026-09-09 (uncommitted). Sits below the locked [[perf-team-direction]] section; both wrapped in the same `rounded-2xl border border-border bg-muted/20 p-5 sm:p-6` container, separated by `mt-6`.

**Backend (new):** `GET /api/performance/cycles/{id}/plans/roster` → `TeamRosterDto` (summary counts + `TeamRosterMemberDto[]`). The existing `plans/reviews` only returns *Submitted* plans, so it couldn't drive a full roster. New `GetTeamRosterQuery`/handler in `PlansFeature.cs`; `PlansComposer.ToRosterMember` + `ResolveRosterActivity`; enums `RosterPlanStatus` (NotStarted/Draft/ReturnedForChanges/Submitted/Approved) + `RosterActivityKind` in `PerformanceContracts.cs`. Roster membership = Participants where `ManagerEmployeeId == caller` (admin sees all); decision authority (`CanReview`) is the responsible-manager relationship on a Submitted plan — deliberately NOT implied by membership. NotStarted = no plan; ReturnedForChanges = Draft whose latest PlanDecision is Returned; progress via `ProgressCalc.PlanProgress`; latest activity = single most-recent event kept as its true kind (approved-but-not-reporting shows no activity, never a fake approval timestamp).

**canView gating (bug fix):** a manager may open a report's plan only once it has been *put forward* — `hasBeenPutForward = plan.State != Draft || plan.Decisions.Count > 0`. A never-submitted Draft is the employee's private workspace, so `canView=false` → roster shows no action + no name link. Reason: the canonical reviewer surface (`plan-review.tsx`) only speaks Submitted/Returned/Approved and falls through to labelling ANY other state as "Submitted" — so opening a pristine Draft there mislabeled it as Submitted with no decision buttons. Returned-for-changes (Draft + a Returned decision) still opens and labels correctly.

**Frontend:** `features/performance/components/team/your-people.tsx` (grid "table", not a real `<table>`), driven by `useTeamRoster` (page owns the query, passes `roster` prop; also drives the page heading count). Search + filter chips (All/Needs review/Planning/Approved/No progress) + Name A–Z/Z–A sort + client pagination (8/page). Submitted row gets amber tint + primary left-marker + "Review plan"; quiet "View plan →" elsewhere; truthful `—` / "No progress reported yet" (never fake 0%). Rows link to canonical `/team/{planId}`. Only semantic DS tokens (dark-safe). Replaced `PlanReviewQueue` on the page (now orphaned, left in place).

**Hana demo seed** (asteria-demo, cycle `af209517-4c1a-4c57-adbf-b3861c00e211`): `.../scratchpad/seed-hana-people.sql` adds 12 reports under Hana (`f633ae63-…`) in mixed states → 14 total (2 needs-review, 6 planning, 6 approved, 2 no-progress), all rows tagged `CreatedBy='seed:hana-people'`. **Revert:** `DELETE FROM performance."Objectives" WHERE "CreatedBy"='seed:hana-people'; DELETE FROM performance."PlanDecisions" WHERE "CreatedBy"='seed:hana-people'; DELETE FROM performance."EmployeePlans" WHERE "CreatedBy"='seed:hana-people'; DELETE FROM performance."Participants" WHERE "CreatedBy"='seed:hana-people';` (that order — FK-safe). Seeded EmployeeIds `e0000000-…-0001..0012` are synthetic (roster reads Participant/plan snapshots, not live Core), so opening a seeded person's plan detail may show blank names.
