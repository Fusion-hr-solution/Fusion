Public auth/onboarding surfaces were redesigned 2026-09-11 from user mockups, intentionally **forced dark in every theme** (brand consistency), using **Fusion DS amber primary** (not the mockups' blue) and the canonical shadcn DS primitives (`Field`/`FieldGroup`/`FieldLabel`/`InputGroup`/`InputGroupAddon`/`InputGroupInput`/`InputGroupButton`/`Alert`) rather than hand-rolled markup.

- **Sign-in** (`packages/auth/src/components/signin-page.tsx`): migrated the auth package off legacy `@repo/ui` → `@repo/ds` (added workspace dep + lockfile). Centered card, `F` monogram + Fusion wordmark, email/password w/ leading icons + eye toggle, remember-me, "or" divider, no-op "Sign in with SSO", Terms footer. Test disambiguated (SSO button also matched `/sign in/i` → submit query is now exact `name:"Sign in"`); dropped the old invitation-helper-copy assertion.
- **Invite acceptance** (shell admin journey `apps/shell/src/app/activate-invitation/activate-invitation.tsx` + shared `@repo/ds/shell` `InvitationTransactionFrame`): two-pane brand shell (left = "Join {tenant}" serif hero + context card [Organization/Assigned role/Invitation sent to] + security note + "PEOPLE WORK TOGETHER"; right = "Set up your account" + First/Last + read-only Work email + Create/Confirm password + green requirements checklist incl. "Passwords match" + "Set up account →" + "Already have a Fusion account? Sign in"). Journeys gained `roleLabel` + `formLead`; `formHeading`→"Set up your account". Frame + loading + terminal frames all forced dark.

**Why:** user wants a distinctive, polished auth identity, dark, on the real DS — not generic SaaS. **How to apply:** for any further auth/onboarding surface, force dark, compose with DS Field/InputGroup, amber as the single accent. Rendered QA via repo Playwright in `apps/shell` (intercept the identity inspect fetch to stub an `account_creation` entry — Identity :5101 needn't run).

Scope chosen: shared frame + shell admin only. **Core workforce `/core/invite/accept` inherits the new dark frame but its form is NOT yet rebuilt to the mockup — parity is a deferred follow-up pass.** All uncommitted. ## 2026-09-11 follow-up (invite acceptance polish, per earlier product spec)
- **Password policy SIMPLIFIED platform-wide.** `AccountPasswordPolicy.cs` now = min **10**, **a letter (either case)**, **a number**, max **128**; uppercase/symbol allowed not required. "A letter" + max-128 needed custom `IPasswordValidator`s (`LetterPasswordValidator`, `MaximumLengthPasswordValidator`) registered in `ServiceCollectionExtensions.cs` (Identity has no case-insensitive-letter option). Requirements record + `@repo/api` DTO + shell `PasswordRequirements` extended ADDITIVELY (`RequiresLetter`, `MaximumLength`) so the deferred workforce form still compiles. This policy applies to ALL account creation, not just invites.
- **c-input-23 strength meter**: `apps/shell/src/app/activate-invitation/password-strength-field.tsx` — faithful reui c-input-23 pattern rebuilt on DS (segmented 5-bar advisory meter weak/medium/strong + Check/X requirement list). Required rules (from `passwordChecks`) gate the CTA; meter is advisory only (rewards optional upper/symbol), never blocks.
- **Name + role wired from the invitation**: inspect responses (tenant-activation + administrator-invitation) now return `firstName`/`lastName`/`role` (mapped from `InviteToken.FirstName/LastName/Role`; bootstrap may be null → fields empty). Frontend prefills names, shows role in context card (falls back to journey `roleLabel` when role has no space, i.e. looks like a key).
- **CTA gated**: "Set up account" disabled until names + 3 password rules + match. Read-only email kept as a tag (no caption, per [[ui-no-explanatory-text]]).
- **Name prefill root cause + fix (2026-09-11):** admin-to-admin invites already captured FirstName/LastName, but the **bootstrap** (first-admin, from platform provisioning) path never did — `CreateOrganizationBootstrap` + `ProvisionTenantRequest` only took email, so first-admin activation always showed empty names. Fixed end-to-end: `ProvisionTenantRequest.AdministratorFirstName/LastName` (optional, NOT in idempotency fingerprint) → `CreateOrganizationBootstrap(...firstName,lastName)` → stored on InviteToken. Platform new-tenant form ALREADY collected first/last name in its draft — it just wasn't sending them; added them to `ProvisionTenantInput` + the submit mapping. **Not retroactive** — invites created before this change stay empty; provision a NEW tenant to see prefill. Verified in hris_identity DB (bootstrap InviteToken now persists the name). Bootstrap Role=`OrgAdmin` (no space) → frontend shows journey fallback "Tenant Administrator" for the role label.
- Also: password requirement rules laid out on one wrapping row (not a column); lock icon removed from the read-only Work email field.
